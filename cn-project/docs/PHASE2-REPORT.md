## Resilience tests and learning summary

**A. Backup DNS.** Mac 2 serves both private names with TTL 30. [Both clients list both nameservers for `solo.test`](../evidence/phase2/06-client-scope.txt). The [raw capture](../evidence/phase2/A-backup-dns.pcapng) confirms the backup reply to Mac 3 with TTL 30. [Live observations](../evidence/phase2/07-backup-dns-observations.txt) record the primary timeout, successful HTTPS and primary recovery on Mac 2. DNS redundancy addresses name resolution. Application availability still depends on the edge and upstreams.

**B. DNS TTL and record change.** Both live resolvers [return a 30-second TTL](../evidence/phase2/08-matching-dns-ttl.txt) for both names after Abhi moved to the shared config. In the [live test](../evidence/phase2/13-live-cutover.txt), fresh queries first showed standby at 00:03:36 and the normal macOS HTTPS request first showed standby at 00:04:09. The [manual flush trial](../evidence/phase2/14-rollback-and-flush.txt) recorded standby before rollback and primary after flushing. A request between the DNS rollback and the flush would isolate the effect of the flush from natural expiry, as the lab did. The TTL sets the retention time for cached answers, so clients can briefly reach different edges during migration.

**C. Backend isolation.** A temporary PF anchor on Mac 3 permits Mac 2's IPv4 source to reach the two inbound Wi-Fi application ports and blocks other sources there. The Mac 3 standby uses loopback. The [LAN baseline](../evidence/phase2/15-firewall-baseline.txt) confirmed Mac 1 and Mac 2 could reach both backend ports before isolation. [With the anchor active](../evidence/phase2/16-firewall-active.txt), both ports timed out from Mac 1 and returned HTTP `200` from Mac 2. Mac 1 still reached the app over HTTPS through the primary edge. The [rollback evidence](../evidence/phase2/17-firewall-rollback.txt) captures packet counts on each rule and direct access returning from Mac 1 after removing the temporary rules.

**D. Backend failover.** nginx uses passive failure accounting, shared across workers, and retries on a healthy upstream. The [live baseline](../evidence/phase2/18-backend-failover-baseline.txt) alternated A and B. With A stopped, the primary [returned six HTTPS `200` responses from B](../evidence/phase2/19-backend-a-stopped.txt), and nginx logged a connection refusal on port `3001`. Once A returned, [both IDs appeared again](../evidence/phase2/20-backend-recovered.txt). Co-located processes survive the loss of one process. Loss of Mac 3 removes both, and Mac 2 is still the primary ingress during normal operation.

**E. Edge migration.** The Phase 2 nginx configs report their identity in `X-Edge`. Mac 2 [signed and verified the standby leaf](../evidence/phase2/09-standby-tls-issued.txt) using the existing CA and an independent random serial. [Live requests to Raghav's standby](../evidence/phase2/10-standby-https-live.txt) proved trusted HTTPS and A/B responses for both names. The [live cutover](../evidence/phase2/13-live-cutover.txt) moved `app.solo.test` to the standby with HTTPS `200` in all 22 samples. `api.solo.test` remained on the primary. The [rollback check](../evidence/phase2/14-rollback-and-flush.txt) verified both names on Mac 2 again and trusted HTTPS through the primary. Keeping both edges running during migration gives cached clients time to move.

**F. Troubleshooting.** The procedure checks DNS, TCP, TLS, then the HTTP response. The [team rehearsal](../evidence/phase2/21-troubleshooting-rehearsal.txt) resolved the private name successfully and reproduced a TCP refusal at the wrong port. Correcting the URL restored HTTPS. At evaluation record the faculty's fault, the first failing layer, the recovery or isolation, and the outcome of the same request afterward. The faculty challenge result is pending.
